# wechat-html-paster

> HTML → 微信公众号 · 内联样式粘贴 + 可视化排版编辑器（单文件，零依赖，浏览器直接打开）

把任意 HTML 文章（含 `<style>`、CSS 变量、`@media`）转换成**全内联样式**的公众号兼容 HTML，并提供 Word 式菜单排版工具条，改完一键复制进 `mp.weixin.qq.com`。

**当前版本：v3.12.0** · 版本历史见 [CHANGELOG.md](./CHANGELOG.md) · 研究与设计见 [docs/PLAN-v3.0.0.md](./docs/PLAN-v3.0.0.md)

---

## 主题色（复刻 nihaotk 的一键全局改色）

nihaotk 用 `:root{--md-primary-color}` + 变量驱动的主题样式表实现整篇重绘。本工具输入是**任意 HTML**，因此改用等价的**基线重导**方案：

1. **转换时登记基线**：逐元素、逐属性记录颜色原值，并判定它是否属于「原始品牌色族」（色相差 ≤14°、饱和度差 ≤0.30）。
2. **换色时从基线重导**：把色族成员映射到主题色，**保留 alpha**（浅色底纹跟着走）、**保留与品牌色的明度/饱和度差**（深色描边、浅色底一起走）。
3. 因此：无关配色（如文章里的红色引用块）永不误伤；反复往返切换**零漂移**（逐字节一致）。
4. 「**还原**」回到转换时的原始配色。

主题色板与 nihaotk **完全一致**（11 色，带名称与色块，三列）：

| 经典蓝 | 翡翠绿 | 活力橘 | 柠檬黄 | 薰衣紫 | 天空蓝 |
|---|---|---|---|---|---|
| `#0F4C81` | `#009874` | `#FA5151` | `#FECE00` | `#92617E` | `#55C9EA` |

| 玫瑰金 | 橄榄绿 | 石墨黑 | 雾烟灰 | 樱花粉 |
|---|---|---|---|---|
| `#B76E79` | `#556B2F` | `#333333` | `#A9A9A9` | `#FFB7C5` |

## 主题色（按角色施加，对齐 nihaotk）

主题色**只作用于这几类角色**，正文段落文字颜色不受影响：

| 角色 | 表现 |
|---|---|
| **小节标题** | 文字色跟随（默认）；或按「标题样式」改为下边框 / 左边框；标题原有的装饰线也一起换色 |
| **卡片 / 引用块** | 边框线条换色；**浅色底纹**按「与白底合成后的观感」换色（保留原透明度与明度） |
| **段落中重要的第一句话** | 段首 `strong` / `b` 文字色跟随 |
| **表格表头 / 分割线** | 表头底色、分割线颜色跟随 |

- 11 个预设色与 nihaotk 实测取色**完全一致**（经典蓝 `#0F4C81` … 樱花粉 `#FFB7C5`）。
- 角色以「元素 + 原值」登记，换色时**从原值重新推导**：往返切换零漂移；插入新元素增量登记；撤销/重做后自动重新登记。
- 「还原」回到转换时识别到的原始品牌色。
- **界面控件（复制 / 转换按钮、版本徽章）使用独立的 `--ui` 色，不随文章主题色变化。**

## 色块 vs 卡片（明确区分）

| | **色块** | **卡片** |
|---|---|---|
| 形态 | 底色 + **同色系细边**（`background + 1px 同色系 border + padding + radius`） | 白色/浅底色 + **主题色边框**（`border(1~4px)`） |
| 插入 | 插入 → 色块 | 插入 → 卡片 / 引用卡片 |
| 编辑 | 样式 → 色块（底色 / **边框：颜色·位置（全/左/无）·宽度** / 清除底色 / 删除色块（保留文字）） | 样式 → 卡片（背景 / 边框色 / 位置 / 宽度 / 移除） |
| 自动识别 | 有底色/渐变底/只有圆角或内边距（含段落级底色、行内高亮） | 有可见边框（含 `blockquote`、`td` 底色等） |
| 状态栏 | 显示「目标：色块」 | 显示「目标：卡片」 |

普通段落（如主体容器里的 `<p>`）识别为「段落」，不会被误判成卡片而错改主体容器。

## 公众号《内容结构检测》合规

对照官方规范 [plugin_spec](https://developers.weixin.qq.com/doc/service/guide/product/plugin_spec.html) 与官方校验器实现 [verify-article-structure-spec](https://github.com/wechatjs/verify-article-structure-spec)（逐条移植为本地自检）：

| 规范 | 判定条件（来自官方源码） | 本工具 |
|---|---|---|
| **3 字体** | 内联 `font-family` **不以 `"mp-quote", PingFang SC, system-ui, -apple-system` 开头即违规** | ✅ **一律不输出 `font-family`**（这是 v2 仍然告警的根因） |
| 1.6 text-align | 值 `start` / `end` | ✅ 内联时丢弃 |
| 1.4 width | `img`、**`table > thead > th`**、非 img/svg 的固定宽度（非 `auto`/`100%`） | ✅ **`thead/th` 自动归一为 `tbody/td`**（样式保留、视觉不变）；宽高全部剥离 |
| 1.5 height | `height:0` 且有文字 | ✅ 不输出 |
| 1.8 pre | `<pre>` 且有文字 | ✅ `white-space:pre` → `pre-wrap`，无 `pre` 标签 |
| 1.1 opacity / 1.2 caret-color | `img` 透明、光标透明 | ✅ 白名单不含 |
| 1.3 line-height | **`lineHeight===0` 或 实测平均行高 < `fontSize×0.95`**（官方 `layout.ts#detectLineHeightOverlap`） | ✅ 转换时 + 导出前两次**行高合规归一**：含文字元素若行高为 0 或小于字号，抬到 `1.2×字号`；自检含两个真实场景夹具 |
| 1.4.2 溢出 | 内容超出移动端宽度 | ✅ 375px 实测无横向溢出 |
| 2.1 嵌套 | 深度 ≥ **15**（源码 `MAX_STYLE_LEVEL`）且存在可删冗余层 | ✅ 输出深度约 6，导出前再扁平化 |
| 2.2 / 2.3 | `span[leaf]` / `section[nodeleaf]` 违规包裹 | ✅ 不产生这两个标记 |
| **结构合法性** | ① 块级元素嵌在段落里（`<p>…<section>…</section>…</p>`）会被微信编辑器**整块丢弃**；② 同标签单子节点嵌套会被「自动精简层级」，多包一层会连背景一起丢 | ✅ 插入时把段落切成前/中/后三段；色块/卡片使用**单层 `<section>`**（背景与文字样式同层、内容直接在内）；`normalizeNesting()` 安全网在转换后、插入后、导出前清理非法嵌套 |
| **`div` 标签** | 微信 ProseMirror 会把 `div` **整段吞掉**（其上的背景/圆角/内边距全丢） | ✅ 输出前递归把**所有 `div` 换成 `section`**（`wechatSafe()`） |
| **无边框容器** | 微信会**丢弃「只有底色、没有边框」的容器**（色块会消失） | ✅ 色块默认带**同色系细边**；如需纯底色可在「样式 → 色块」切换为无边框（有被过滤风险） |
| **背景色** | 微信对 `rgba()` 背景过滤较严 | ✅ 背景一律输出**不透明 `rgb()`**；**透明背景一律不输出**（否则会给每个元素刷一层白，盖住色块底色 —— v3.7 曾因此出 bug） |
| **默认外边距** | 输出里省略零 `margin` 会让微信套用默认外边距（`h1` 0.67em、`p` 1em），标题与正文间距变大 | ✅ 零 `margin` **一律显式输出**（零 `padding` 仍省略，列表类保留） |
| 输出体积 | 内联冗余导致粘贴卡顿 | ✅ no-op 声明裁剪，样例 32KB → **5.8KB** |

## 快速使用

1. 浏览器打开 `wechat-html-paster.html`（Chrome / Edge）。
2. 「文件 → 载入样例」或直接粘贴 HTML → 「转换并适配公众号」`Ctrl+↵`。
3. 右侧预览**选中文字**，用「格式 / 样式」菜单改字号、颜色、行距、底色、边框；「插入」加色块/卡片；「样式 → 主题色」一键换整篇配色。
4. 「复制」`Ctrl+Shift+C` → 去公众号后台 `Ctrl+V`。

## 粘贴时提示「行高小于字体大小」（2.3.2 误报）

症状：粘进公众号编辑器后弹出《内容结构检测》，报几十个段落「行高小于字体大小，且存在多行文本，
可能导致文字重叠（实测）」，参考文档 `#2.3.2 line-height-overlapping`。手机预览里排版其实是好的。

**这是官方检测器的误报**，根因在 `cli/engine/layout.ts`：

```js
// ① 只挑「块元素里有直接文本子节点」的节点来测
if (![...node.childNodes].some(c => c.nodeType === TEXT_NODE && c.textContent.trim())) return;
// ② 用 range 的「片段数」当行数
const rects = [...range.getClientRects()].filter(r => r.height > 0);
const lineCount = rects.length;                          // ← 不是视觉行数
// ③ 平均行高 < 0.95×字号 即判叠字
overlapping = lineCount >= 2 && (range 内容高 / lineCount) < fontSize * 0.95;
```

`range.getClientRects()` 按「行内盒 × 行片段」返回矩形，所以**段落里每多一个 `<strong>`/`<span>`，
每行就多出若干"片段"**，而内容高只按真实行数增长 → 平均行高被腰斩。实测（`16px/29px` = 1.8 倍行高）：

| 段落形态 | range 片段数 | 判定 |
|---|---|---|
| 纯文本 3 行 | 3 | ✅ 通过 |
| **中间一个 `<strong>`** | **5~6** | ❌ **报叠字** |
| 每行若干 `<span>` | 13 | ❌ 报叠字 |

### 本工具怎么处理
把「块元素的**直接文本**」包进带样式的 `<span>`（span 带上与块相同的 `font-size/line-height/color/font-weight`，
值相同不影响排版，只是为了让微信 ProseMirror 保留它）。于是官方 fallback 路径不再量这些块，
改由 rules 路径按「每个行内片段自身」测量 —— 片段自身的 rect 数就是真实行数，天然合格。

实测（用户样例推文，585px 沙箱）：

```
修复前  官方 fallback 告警 35 处
修复后  官方 fallback 告警  0 处
逐块高度序列（p/section/li/td/h*）：完全一致 —— 版式一个字没变
输出体积：33475 → 41920 字节（+25%，125 个合规 span）
```

发之前可以点**帮助 →「结构检测预演」**：在本地用同一算法跑两条路径（fallback / rules）自检，
发现问题会自动修一次并复检，不用等公众号报警。

> 教训：移植官方校验器时，测量 API 必须是 `range.getClientRects()`（内容矩形），
> 不能用 `el.getClientRects()`（元素矩形，块元素恒为 1）—— 后者会给出假绿灯。
> 合规套件现在按官方源码逐字移植，并含「段落中间一个 `<strong>`、行高 1.8 倍」这个真凶 fixture。

## 粘到公众号后正文变窄（左右留白叠加）

症状：工具里排版正常，粘进公众号编辑器后正文明显缩窄、页边距变大，而编辑器「两端缩进」已经是 0。

原因是**两层左右留白叠加，而预览只显示了一层**：

| 层 | 来源 | 数值（样例推文） | 能不能去掉 |
|---|---|---|---|
| ① 稿件自带 | 原页面的外层容器内边距，被拍平成根 `<section>` 的 `padding` | `padding:44px 38px` → 左右各 38px | ✅ 点「左右归零」 |
| ② 公众号自带 | 微信文章页面自己的左右留白 | **20px/侧**（官方 CSS `--appmsgPageGap: 20px`） | ❌ **去不掉** |

第二层的证据在**微信官方 CSS** 里：`公众号文章页根变量 --appmsgPageGap: 20px`，PC 皮肤正文区 `max-width: calc(677px + var(--appmsgPageGap) * 2)` —— 正文内容宽 677px、两侧各 20px。
所以**手机 375px 上正文字宽上限 = 375 − 2×20 = 335px**，这层留白不在你粘贴的 HTML 里，任何工具都改不掉。

**关键教训：不要试图用负 `margin` 抵消第②层 —— 实测无效。** 微信编辑器画布会裁切/重置最外层负边距，
`margin-left:-15px` 粘进去后正文宽度一点没变（用户实测反馈）。所以正确的做法不是跟微信较劲，
而是**把第②层模拟进预览**，让工具里看到的宽度 = 公众号里的宽度：

- **「预览模拟微信留白」**（默认 20px = 微信官方值，可校准）：把 `#preview` 外壳按这个值内缩，
  于是预览真实版心 = 578 − 2×20 = 536px，与公众号一致。**它只作用在预览外壳上，不会写进导出的正文 HTML。**
  如果你公众号里实际看到的宽度不同，把这个值调到一样即可（0/8/15/20/24）。
- **留白体检**：实时显示「稿子自带 左 X · 右 Y（预览真实版心 N，正文 M）」+「微信自带 20px/侧（已模拟）」+「手机上限 335px」
  +「手机 375px 下正文约 Z」。三项自洽：左 + 正文 + 右 = 版心。正文代表块取最长的那段**普通段落**，
  不会被开头的小标签/胶囊带偏。
- **左右归零**：把正文外层链路（根 + 页面级容器）的左右 `padding`/`margin` 清零；色块、卡片这类设计元素不动。
- **版心参考线**：用红色虚线画出微信自带那 20px 的位置。

样例这份稿子的实际数字：

```
稿件自带 38px/侧 →  预览正文 470px   手机 375px 下约 269px
左右归零后        →  预览正文 536px   手机 375px 下 335px  ← 上限（375 − 2×20）
```

也就是说：**能控制的只有第①层**，清掉它就是公众号里能达到的最大宽度；第②层所有工具都躲不掉（md.nihaotk 也一样，
只是它的产物没有第①层，所以看起来"没问题"）。

### ⚠️ 坑：改了设置却"没改善"

正文是**每次点「转换」时从原稿重新拍平**的（原稿的 `.container{padding:44px 38px}` 会被重新写成内联样式）。
所以早期版本里，`页边距` / `左右归零` 只改当前这一次结果，**再点一次「转换」原稿留白就回来了** ——
用户就会以为"改了没用、公众号里还是老样子"。

现在：

- `页边距（左右/上下）`、`转换时自动左右归零`、`预览模拟微信留白` 都存进 `localStorage['wxp.layout.v1']`，
  **每次转换结束后自动重放**（先自动归零，再叠加显式页边距，显式设置优先）；重开工具也记得。
- 点「左右归零（正文变最宽）」会**自动勾上**「转换时自动左右归零」，一次设置长期生效。
- `预览模拟微信留白` 下拉**只影响预览显示，不改正文**（为了让预览 = 公众号观感）。
- 想知道微信那层到底是多少：在公众号编辑器里**全选 → 复制 → 粘回输入框 → 点转换**，
  此时体检里的「稿子自带左右留白」就是微信那层的真实值，把「预览模拟微信留白」调到一致即可。

### 一键定位「谁在吃宽度」：版心诊断

分不清「已经最宽了」还是「还有东西在吃宽度」时，点**样式 → 页边距 →「版心诊断（可复制）」**，
它会输出一份可直接粘给他人排查的报告：版心 / 正文字宽 / 左右留白 / 手机估算宽度、
从根到正文每层容器的宽与内外边距与 `display`、**宽度去哪了**（点名是哪一层的内边距或哪个窄容器）、
以及结论（「还有 XXpx 可回收」还是「已等于版心，剩下的只可能来自微信自身」），
最后附上最外层标签与样式。结果自动进剪贴板，面板里也留一份可手动选中的副本。

## 转换管线与样式隔离

> 输出前会跑一遍 **`wechatSafe()`**：`div`→`section`、`rgba`→实色 `rgb`、剥掉 HTML 表现属性（`width/align/bgcolor`…）、表格补 `width:100%`。


```
原文 HTML ─► DOMParser 取 <style>
                 │
                 ▼
     ┌──────────────────────────────┐
     │ 隐藏 iframe 沙箱（578px）     │  ← 文章 CSS 只作用于 iframe，不污染工具界面
     │ <style> + body 内容           │
     └──────────────────────────────┘
                 │ iframe.contentWindow.getComputedStyle
                 ▼
    白名单内联（丢弃 font-family / text-align:start|end，pre→pre-wrap，no-op 降噪）
                 │ sanitize（去 class/id）+ thead/th → tbody/td
                 ▼
    <section> … </section> ─► 基线登记 ─► 主题色重绘 ─► 预览 / 复制 / 下载
```

## 开发说明

- 零依赖、零构建：纯原生 HTML + CSS + JS。
- 撤销/重做：innerHTML 快照栈（80 步）；DOM 被整体替换后自动以当前主题色重新登记基线。
- 工具条按钮 `mousedown` 不抢焦点，保住预览区选区。
- 分栏宽度、主题色等状态不写服务端；分栏宽度存 localStorage。
